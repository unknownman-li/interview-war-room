## 2. 简历项目描述（可直接替换）

### 项目简介

基于 Spring Boot 的本地生活优惠券交易平台，覆盖商户/优惠券检索、抢购、订单支付与超时关闭。系统面向高并发抢购场景，以 Redis 预扣、消息队列削峰、消费重试和数据库对账保障最终一致性。

### 核心工作

- **抢购全链路一致性**：设计「ZSET 滑动窗口双限流 → Redis + Lua 原子预扣（库存校验 + 一人一单）→ Pending 中间态 → RabbitMQ 异步落库 → 消费重试 → DB 定时对账」链路。预扣与落库解耦，削峰的同时保证预扣成功后的订单状态可查；发送或消费失败通过重试和告警暴露，最终以 MySQL 为事实源对账收敛 Redis/DB 库存差异，避免超卖与少卖。

- **可靠消息与可观测**：生产端开启 Publisher Confirms，队列与消息持久化；消费端手动 ACK + 重试队列，业务唯一键保证幂等落库；全链路 traceId 贯穿生产消费，Prometheus 监控投递成功率、消费延迟与积压，异常可定位到具体消息。

- **缓存防护闭环**：布隆过滤器前置拦截无效请求，空值缓存兜底剩余穿透；互斥锁与逻辑过期分别应对强一致/高可用场景的击穿；写链路采用 Cache-Aside，更新 DB 后删除缓存，删除失败经 MQ 重试，TTL 最终兜底；Caffeine（L1）+ Redis（L2）两级缓存，热点读 QPS 1.5w → 9w，平均延迟 48.09ms → 11.21ms。

- **超时订单与支付/关单并发**：延迟消息（TTL + DLX）触发到期关单，xxl-job 周期扫描 DB 兜底，消费者幂等执行；支付与关单通过状态机 + 乐观锁条件更新，避免重复支付和已支付订单被误关。

- **检索与异步解耦（可选）**：商户/优惠券检索基于 Elasticsearch；通知、积分、统计等非核心链路走 MQ 解耦，避免拖慢主交易链路。

## 3. 口述版本

### 30 秒版

> 我做的项目是一个本地生活优惠券交易平台，核心是高并发抢购。抢购链路先用 ZSET 做用户级和券级滑动窗口限流，再用 Redis + Lua 原子完成库存预扣和一人一单，预扣后落 Pending，通过 RabbitMQ 异步落库削峰；失败由重试和定时对账兜底，以 DB 为准修正 Redis 库存。缓存侧做了布隆过滤器、空值缓存、互斥锁/逻辑过期和 Caffeine + Redis 两级缓存，读 QPS 从 1.5w 提到 9w。超时订单用延迟消息加定时任务双保险。重点是让「不超卖、不丢消息、缓存最终一致、订单能闭环」这四件事真正落地。

### 1 分钟版

> 这个项目是本地生活优惠券交易平台，我主要负责抢购链路和缓存一致性。
>
> 抢购时先用 ZSET 做用户级和券级的滑动窗口限流，把刷单和突发流量挡在前面；然后用 Redis + Lua 原子完成库存校验、一人一单和预扣。预扣成功后先落一条 Pending 记录，保证用户马上能查到订单状态；真正的落库通过 RabbitMQ 异步做，起到削峰填谷的作用。
>
> 消费端手动 ACK，失败进重试队列，并用业务唯一键做幂等；如果最终还是失败，会记录失败并告警，同时靠定时对账以 DB 为准修正 Redis 库存。
>
> 缓存这块，穿透用布隆过滤器加空值缓存，击穿用互斥锁和逻辑过期两套方案；写链路是 Cache-Aside，删缓存失败用 MQ 重试，TTL 兜底。本地 Caffeine + Redis 两级缓存，读 QPS 从 1.5w 提到 9w，平均延迟从 48ms 降到 11ms。
>
> 超时订单用 TTL + DLX 延迟消息加 xxl-job 扫描双保险，支付和关单用状态机加乐观锁防止并发冲突。整条链路有 traceId 和 Prometheus 监控。

### 3 分钟版结构

1. **背景**：本地生活优惠券，抢购瞬间流量高，核心矛盾是库存、缓存、消息、订单状态。
2. **抢购链路**：限流 → 预扣 → Pending → MQ → 落库 → 重试/对账。
3. **缓存链路**：穿透、击穿、写一致性、两级缓存。
4. **订单闭环**：延迟消息 + 定时任务 + 状态机 + 乐观锁。
5. **可观测**：traceId、Prometheus、积压和投递失败监控。
6. **结果与取舍**：QPS/延迟数据；哪些地方选择了最终一致而不是强一致，为什么。

## 4. 架构与关键链路

### 抢购链路

```text
客户端
  │
  ▼
接入层 ── ZSET 滑动窗口限流（用户级 + 券级）
  │
  ▼
抢购服务
  ├─ Redis + Lua：库存校验 + 一人一单 + 预扣
  ├─ 写 Pending 记录（状态可查）
  └─ 发送 RabbitMQ 消息
        │
        ▼
   订单消费服务
     ├─ 幂等校验（业务唯一键）
     ├─ MySQL 落单 + 条件更新扣库存
     ├─ 成功 → 更新订单状态
     └─ 失败 → 重试队列 → 记录失败 + 告警
        │
        ▼
   定时对账 / Prometheus + traceId
```

### 缓存读写链路

```text
读：请求 → Caffeine L1 → Redis L2 → 布隆过滤器 → MySQL
                              ▲
写：更新 MySQL → 删除 Redis → 删除失败进 MQ 重试 → TTL 兜底
```

### 三个关键设计

1. **Pending 中间态**：预扣成功但尚未落库时，用户能看到「处理中」，而不是查不到订单；也方便超时取消和补偿。
2. **重试 + 幂等**：消费失败进重试队列，消费端用业务唯一键和状态机条件更新保证重复消息不会重复落单。
3. **DB 对账**：消息重试仍失败时记录并告警，最终以 MySQL 为准做定时对账，发现 Redis/DB 库存差异后修正。

## 5. 高频追问与答法

### Q1：为什么预扣后要 Pending，不直接异步落库？

预扣只是锁定资格，不是最终订单。Pending 让状态可查，避免「库存扣了但订单查不到」；同时给落库、重试、超时取消留出状态机空间。

### Q2：Redis 预扣成功但 MQ 发送失败怎么办？

当前实现是发送失败重试并记录，配合定时对账兜底；预扣和发消息不是严格原子操作，极端情况下会以 DB 为准修正。面试时可以主动说明这个边界，不要硬说成强一致。如果要做更严格，需要额外的一致性方案，但复杂度和运维成本会明显上升。

### Q3：消息重复消费怎么幂等？

三层：业务唯一键（userId + couponId + requestId）唯一索引；Redis SETNX 前置拦截；状态机条件更新（只有 Pending 才能变成成功），重复消息不会重复落单。

### Q4：Redis 和 DB 库存不一致怎么发现和修复？

DB 是最终事实源。定时对账按券维度比对可售/已售库存，差异告警后回滚或补扣；失败消息记录和库存变更流水用于追查。

### Q5：为什么用逻辑过期而不是互斥锁？

互斥锁保证强一致，但热点 key 重建时会阻塞大量读请求；逻辑过期返回旧值 + 异步重建，可用性更高，接受短时间不一致。对一致性要求高的数据用互斥锁，对热点读用逻辑过期，要看业务取舍。

### Q6：删除缓存失败怎么办？

写链路是 Cache-Aside：更新 DB 后删除缓存，删除失败把任务投递到 MQ 重试，同时设置 TTL 做最终兜底，避免脏数据长期存在。极端情况下靠对账和告警发现。

### Q7：延迟消息和定时任务为什么要双保险？

消息可能丢、延迟不准、消费失败；xxl-job 扫描 DB 是最终兜底。关单必须幂等，避免重复关闭或误关已支付订单。

### Q8：两级缓存一致性怎么保证？

L1 多实例，更新 DB 后先删 Redis，再通过 MQ/Redis pubsub 广播失效 L1；或者 L1 只存极热点数据 + 短 TTL。不要假设本地缓存能强一致。

### Q9：限流为什么用 ZSET？

滑动窗口精确，能实现用户级/券级双限流；成本是内存和 O(logN)。更大流量可以换 Redis Cell、令牌桶或网关限流。

### Q10：为什么选 RabbitMQ 而不是 Kafka？

交易链路需要低延迟、逐条确认、延迟队列、重试；RabbitMQ 更贴合；Kafka 更适合高吞吐日志/埋点。如果两者都用，明确分工。

## 6. 数据口径（重要）

两份简历里的数字基线不同，不要混着说：

| 口径 | 吞吐 | 延迟 |
| --- | --- | --- |
| 直连 MySQL | 1x | 约 53.15ms（由 53.15 − 11.21 = 41.94 推得） |
| Caffeine + Redis 二级缓存 | 4.95x | 11.21ms（较 MySQL 下降 41.94ms） |
| 加 L1 前 | 1.5w QPS | 48.09ms |
| 加 L1 后 | 9w QPS | 11.21ms（下降 36.88ms） |

面试时建议统一说：

> 「4.95 倍和 41.94ms 是二级缓存相对直连 MySQL 的提升；1.5w 到 9w、48.09ms 到 11.21ms 是加本地 Caffeine 前后的对比。两组基线不同，不要混在一起。」

这样既解释了数字，也显得压测口径清楚。

## 8. 和旧版「本地生活点评平台」的差异

网站当前项目模块还是旧口径：Guava 令牌桶、1000 并发/100 库存、14 次重复/36 次正常、零超卖。新简历已经换成：

- 限流：ZSET 滑动窗口双限流（不是 Guava 令牌桶）
- 一致性：Pending + 消费重试 + DB 定时对账
- 缓存：Caffeine + Redis 两级缓存，删除失败 MQ 重试 + TTL 兜底
- 超时订单：TTL + DLX + xxl-job（旧版是 Spring Task）
- 消息：Publisher Confirms + 手动 ACK + 重试队列 + 幂等

如果继续用新简历投递，网站的项目总览、秒杀、Redis、RabbitMQ、MySQL、登录限流等模块需要同步改写，否则「网站背的内容」和「简历写的项目」会对不上。
